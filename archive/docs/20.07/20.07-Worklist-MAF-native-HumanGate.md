## S0 — Verifikations-Spike: RequestPort + FileSystemJsonCheckpointStore

**Ziel.** Mit Bordmitteln beweisen, dass ein MAF-Workflow an einem Human-Gate pausiert, den State durabel auf Platte
legt und in einem **komplett neuen Prozess** fortgesetzt werden kann.

**Warum (Begründung).** Der gesamte Plan (B und A) steht und fällt mit dieser einen Annahme. Die frühere Behauptung „C#
hat nur In-Memory-Checkpointing" war falsch (siehe Decision §1) — das zeigt: nur die XML-Doc gelesen zu haben reicht
nicht, das **Laufzeitverhalten** muss belegt sein (MAF-First: verifizieren statt annehmen). Ein isolierter Spike kostet
fast nichts, verhindert aber, dass wir `github-forward` auf einer unbewiesenen Prämisse umbauen.

**Vorgehen.**
1. Throwaway-Kommando `spike-hitl` in `Program.cs` + kleiner Graph: `Judge`-Executor (aus dem MAF-Sample) mit
   `RequestPort.Create<NumberSignal,int>("gate")`.
2. `CheckpointManager.CreateJson(new FileSystemJsonCheckpointStore(<runDir>/checkpoints), opts)`.
3. Lauf A: bis `RequestInfoEvent`, `CheckpointInfo` merken (Datei auf Platte prüfen), Prozess **beenden**.
4. Lauf B (**neuer** Prozess): denselben Graph bauen, `InProcessExecution.ResumeAsync(wf, checkpoint, mgr)`,
   auf re-emittiertes `RequestInfoEvent` warten, `SendResponseAsync(req.CreateResponse(x))`, bis `WorkflowOutputEvent`.

**Erwartete Beobachtung.** Lauf B startet ohne Lauf-A-Speicher im RAM, bekommt trotzdem das offene Gate erneut und
terminiert nach der Antwort. Checkpoint-Dateien liegen unter `checkpoints/`.

**Exit-Kriterium.** Prozessübergreifender Human-Gate nachweislich **mit Bordmitteln** (kein Custom-Store). Serialisierung
der Prozess-State-Records funktioniert.

**Evidenzpfad.** `runs/spike-hitl/<runId>/` (Konsolen-Log beider Läufe + checkpoints/).

**Risiken / worauf achten.** (a) `JsonElement`-Serialisierung eigener Records (`IWireMarshaller`) — bewusst simpel
halten. (b) Store-Verzeichnis muss vor Lauf B existieren/lesbar sein. (c) Falls `ResumeAsync` das Event *nicht*
re-emittiert → offene Frage an die Docs/Samples, **bevor** S1 startet.

**Abhängigkeit.** keine. **Kein LLM-Lauf** (der Judge ist deterministisch).

### S0 — ERGEBNIS (2026-07-21): ☑ verifiziert

Gebaut: `hitlspike/HitlSpikeRunner.cs` (Kommando `spike-hitl start|resume`), Dispatch in `Program.cs`. Graph:
`RequestPort.Create<string,int>("hitl-spike-gate")` → `HitlSpikeFinalExecutor : Executor<int>` (YieldsOutput string).
Store: `FileSystemJsonCheckpointStore(<dir>/checkpoints)`, `CheckpointManager.CreateJson(store, opts)`.

**Beleg (Evidenz: `runs/spike-hitl/s0-evidence-20260721_113943/transcript.txt`):**
- Prozess A: erreicht das Gate, `SuperStepCompletedEvent.CompletionInfo.HasPendingRequests==true`, Checkpoint auf Platte,
  Zeiger (`sessionId`+`checkpointId`) persistiert, **Prozess endet**.
- Prozess B (**separater** `dotnet run`): `OpenStreamingAsync` → `RestoreCheckpointAsync` → der **identische**
  `requestId=8c26e841…` wird als `RequestInfoEvent` **erneut emittiert** → `SendResponseAsync(CreateResponse(42))` →
  `WorkflowOutputEvent "Antwort vom Menschen erhalten: 42"` → terminiert. Gleiche requestId über Prozessgrenze = der
  offene Request wurde durabel von Platte wiederhergestellt, nicht neu erzeugt.

**Learnings (wichtig für S1):**
1. **Cross-Process-Muster, das funktioniert:** `InProcessExecution.OpenStreamingAsync(workflow, manager, sessionId)` +
   `run.RestoreCheckpointAsync(checkpoint)` + `WatchStreamAsync`. Das naive `ResumeStreamingAsync(workflow, checkpoint,
   manager)` **hing** in meinem Aufruf (kein Event, kein Output) — für S1 daher das Open+Restore-Muster verwenden.
2. **`[YieldsOutput(typeof(T))]` ist Pflicht** (rc1): der Final-Executor ohne Attribut warf zur Laufzeit
   `ExecutorFailedEvent`/`WorkflowErrorEvent` — analog zur bekannten `[SendsMessage]`-Regel. In `CLAUDE.md`-Learnings
   bereits verankert; hier erneut bestätigt.
3. **`CheckpointInfo(sessionId, checkpointId)`** — Ctor-Reihenfolge (per XML-Doc verifiziert).
4. **Pause-Signal:** `SuperStepCompletedEvent.CompletionInfo.HasPendingRequests` + `.Checkpoint` — sauberer Bruchpunkt als
   auf `RequestInfoEvent` zu brechen (Checkpoint entsteht erst am Superstep-Ende).
5. Der `FileSystemJsonCheckpointStore` legt **pro Superstep** eine Checkpoint-Datei + `index.jsonl` an — durabel,
   inspizierbar.

**Exit-Kriterium erfüllt:** prozessübergreifender Human-Gate mit Bordmitteln nachgewiesen; Serialisierung der
Prozess-State-Records (string/int) funktioniert. → **S1 ist freigegeben.**

## S1 — `github-forward` als Referenzstufe: RequestPort statt CLI-`-review`/`-apply`

**Ziel.** Die kleinste agentische Stufe von „Maker→Gate→Finalize(Plan) + separate CLI-Kommandos `-review`/`-apply`" auf
`Seed → Maker → Gate → [RequestPort Human] → Apply` als **einen** MAF-Lauf mit Checkpoint heben.

**Warum.** `github-forward` ist der beste erste Kandidat: kleinste agentische Stufe, hat den Repair-Loop bereits
(`core/GateLoop.cs`), ein klar umrissenes Human-Gate (LINK vs CREATE), und ein isolierbares, gut testbares Apply. Damit
wird sie die **Referenz-Implementierung**, an der sich S4 orientiert. Der Umbau beweist konkret, dass der CLI-Gate
entbehrlich ist (Kern des Autor-Einwands).

**Vorgehen.**
1. `RequestPort.Create<ForwardDecisionRequest, ForwardDecisionResponse>("forward-gate")` in
   `tor3/GithubForwardWorkflow.cs`.
2. Gate-Verdict-Routing erweitern: `Decision == auto/deterministic` → direkt Apply; sonst → RequestPort (Payload =
   Plan-Zusammenfassung + Anchors/searchEvidence je Op).
3. Neuer `GithubForwardApplyExecutor` (Executor-Variante von `GithubForwardApplyRunner`), konsumiert die
   `ForwardDecisionResponse` und schreibt Mapping/Core **deterministisch, idempotent** (siehe S3).
4. Checkpoint via `FileSystemJsonCheckpointStore` unter `runs/github-forward/<runId>/checkpoints/`.
5. **Core NICHT in den Checkpoint** — nur `pbiId`, `runId`, Plan-Referenz, Decision im Prozess-State (Decision §3.1).
6. Repair-Loop unverändert lassen (nicht anfassen — separater Beleg existiert).

**Erwartete Beobachtung.** `github-forward <run>` läuft als ein Lauf, pausiert am Gate, lässt sich (S0-Muster)
prozessübergreifend fortsetzen; nach der Antwort schreibt Apply das Mapping exakt wie der heutige CLI-Pfad.

**Exit-Kriterium.** Ein MAF-Lauf ersetzt `github-forward` + `-review` + `-apply` funktional; Mapping-Ergebnis identisch
zum alten Pfad (Vergleich gegen einen früheren Referenzlauf, z.B. den 27×-LINK-Lauf); Core-Diff nur die erwarteten
Mappings.

**Evidenzpfad.** `runs/github-forward/<runId>/` (workflow-events, checkpoints, applied/). Vergleichslauf-runId notieren.

**Risiken.** (a) Doppel-Write bei Resume → S3 muss ggf. vorgezogen/mitgebaut werden. (b) Kein Regressions-Bruch am
alten CLI-Pfad → alten Pfad zunächst **parallel** lassen (Feature-Flag/zweites Kommando), nicht sofort löschen.

**Abhängigkeit.** S0 grün.

- Leer-Delta (`s1-verify-empty`): start → Gate pass → **Pause am Human-Gate + Checkpoint** → resume (neuer Prozess) →

  `HOLD_BLOCKED`** → Gate pass → Pause → resume `--accept-all` → Apply: `op-0 HOLD_BLOCKED = held`, success. Ein MAF-Lauf
  hat `forward`+`-review`+`-apply` ersetzt; Plan/Gate/Attempts/Summary + `applied/github-forward-apply-report.json`
  liegen wie beim alten Pfad.

**Invarianten eingehalten:** Plan = Disk-Artefakt; Core NICHT im Checkpoint (Apply lädt frisch); nur die
Review-Entscheidung fließt durch den Port; Repair-Loop unangetastet.

**Learning:** ein Executor darf gleichzeitig `[SendsMessage]` UND `[YieldsOutput]` deklarieren und zur Laufzeit wählen
(Finalize: Port bei Pass, Yield sonst) — bestätigt, `Build()` bricht nicht (bekannte rc1-Eigenschaft).

**Noch offen (bewusst, nicht S1):** echter `--execute`-Lauf gegen GitHub + Core-Mapping (autor-getrieben, Token, Core-
Backup) — deckt LINK/CREATE über den vollen Pfad ab. Der alte CLI-Pfad bleibt als Netz.

## S2 — `AgenticSdlc.HumanReview` an `RequestInfoEvent` anbinden

**Ziel.** Die generische Review-UI wird der Responder auf offene `RequestInfoEvent`s (statt `human-decisions.json`).

**Warum.** Der Human-Gate soll ein echter, sichtbarer Halt sein — die UI existiert bereits (domänenagnostisch). Damit
wird der Kreis „Workflow pausiert → Mensch entscheidet in UI → Workflow resumt" ohne Datei-Zwischenschicht geschlossen.
Der Dateipfad bleibt als Fallback/Testpfad (Automatisierbarkeit von Testläufen).

**Vorgehen.** Adapter: offenen Request lesen → Plan/Anchors rendern → Entscheidung via `SendResponseAsync`
zurückschreiben. `human-decisions.json`-Pfad als alternativer Responder erhalten.

**Erwartete Beobachtung.** In der UI erscheint der offene Forward-Fall; Freigabe treibt denselben Lauf weiter.

**Exit-Kriterium.** Ein `github-forward`-Lauf lässt sich End-to-End nur über die UI abschließen; `human-decisions.json`
weiterhin als Testpfad nutzbar.

**Evidenzpfad.** `runs/github-forward/<runId>/` + UI-Screenshot/Log.

**Risiken.** UI-Prozess ↔ Workflow-Prozess-Grenze: die Antwort muss den laufenden/rehydrierten Run treffen (über
Checkpoint-Resume, S0-Muster). Klar trennen: UI schreibt Response, Host resumt.

**Abhängigkeit.** S1 grün.

### S2 — ERGEBNIS (2026-07-21): ☑ verifiziert

Gebaut in `GithubForwardHitlRunner.ResumeAsync`: neuer Modus `--ui` (opt-in; CLI-Entscheidungen `--accept-all`/`--accept`/
`human-decisions.json` bleiben als Fallback/Testpfad). Beim re-emittierten `RequestInfoEvent` startet `CollectViaUiAsync`
die **bestehende** generische Review-UI (`LocalReviewServerHost` + `GithubForwardReviewAdapter`, derselbe Server/Adapter
wie `github-forward-review`), der Mensch entscheidet apply/skip je Op → `human-decisions.json` (Evidenz) → die Auswahl
wird als `ForwardReviewResponse` per `SendResponseAsync` in den pausierten Lauf zurückgegeben. Im UI-Modus kein enger
Timeout (Mensch darf Zeit haben); `reviewer="human (review-ui)"`.

**Beleg (Mensch per HTTP simuliert, headless):** start → Pause; `resume --ui --no-browser` (Hintergrund) bindet
`http://127.0.0.1:<port>`; via `curl` `POST /api/item/op-0 {decision:skip}` + `POST /api/finish`. Ergebnis:
`UI Finished: 0/1 akzeptiert` → `human-decisions.json` (`reviewer: "human (review-ui)"`, `decision: skip`) →
Apply-Report `op-0 = skipped, accepted=0`. **Bewusst der SKIP-Fall**, um zu zeigen, dass die **UI-Entscheidung** den Lauf
treibt (nicht der Default „apply" und nicht `--accept-all`). Kreis geschlossen: Workflow pausiert (Prozess A) → UI-Halt →
Freigabe → Resume + Apply (Prozess B), ohne Datei-Zwischenschritt als Zwang.

**Learning:** die UI (eigener Kestrel auf `127.0.0.1:0`) läuft IM Resume-Prozess und blockiert, bis der Mensch
`finish`/`cancel` klickt; danach liefert `session.Items` die Entscheidung → sauber in die MAF-Response übersetzbar.

**Noch offen (bewusst):** echter `--execute` gegen GitHub via UI (autor-getrieben, Token, Core-Backup); LLM-Pfad.

## S3 — Apply-Härtung: Idempotenz an den 5 Mutationspunkten

**Ziel.** Ein wiederholter Apply desselben Plans darf **nichts** doppelt schreiben (Core-Items, Mappings, GitHub-Issues).

**Warum.** Das ist die **echte** State-Integritäts-Fläche (Decision §2.4): Core wird an genau 5 Stellen mutiert
(`CoreSeedRunner`, `CoreGithubMapRunner`, `IngestionReviewAdapter`-Apply, `GithubForwardApplyRunner`,
`GithubReverseApply`). Sobald ein Lauf prozessübergreifend resumen kann (S0/S1), wird ein Apply potenziell **mehrfach**
ausgelöst — Idempotenz ist dann Pflicht, nicht Kür. Deterministisch, kein MAF-Thema (Checkpoints lösen das nicht).

**Vorgehen.** Je Mutationspunkt eine Vorbedingung/Marker: „schon angewendet?" (z.B. Op-Id/Plan-Hash im Core oder ein
`applied.marker`). Apply wird zu „ensure state", nicht „append". Für GitHub-Write: vor CREATE erneut Existenz prüfen
(search) — der Anti-Duplikat-Pfad existiert schon, hier nur konsequent auf Re-Run auslegen.

**Erwartete Beobachtung.** Zweimaliger Apply desselben Plans → zweiter Lauf = No-Op (Core-Diff leer, keine neue Issue).

**Exit-Kriterium.** Deterministischer Test: Apply → Apply → identischer State, keine Duplikate.

**Evidenzpfad.** Test-Log + Core-Diff (vorher/nachher identisch).

**Risiken.** Marker-Granularität (Plan-Ebene vs Op-Ebene) — Op-Ebene ist robuster gegen Teil-Applies.

**Abhängigkeit.** Sollte **mit** S1 gebaut oder direkt danach; spätestens vor S4.

### S3 — ERGEBNIS (2026-07-21): ☑ verifiziert

Befund vorab: **`CoreGithubMapping.Apply` ist für LINK bereits idempotent** (ein PBI hält max. EINE
`implemented_by_issue`-Relation → „unchanged" statt Duplikat). Die echte Lücke sind die **append-artigen GitHub-Writes
`CREATE_ISSUE`/`COMMENT`** (Re-Run legt ein Duplikat an).

Gebaut in `GithubForwardApply.ExecuteAsync` (op-level, „ensure state, not append"): Core wird bei `execute` EINMAL vorab
geladen; ein PBI, das im Core bereits gemappt ist, kurzschließt VOR jedem Write mit Status **`already-applied`** —
CREATE: jedes bestehende Mapping zählt; LINK/UPDATE/COMMENT: nur bei gleichem Ziel-Issue (anderes Ziel = echte
Änderung → durchlassen). Neues Summary-Feld `alreadyApplied`. Derselbe vorab geladene Core wird für den Mapping-Write
wiederverwendet (kein Re-Read).

**Beleg (deterministisch, Core-Backup/-Restore, LINK braucht keinen Token):** Fixture LINK `PBI-001 -> gh#999`, zweimal
`github-forward-apply --execute`:
- Lauf 1: `linked=1` → Core-Relation angelegt (1 Mapping).
- Lauf 2 (identischer Plan): `alreadyApplied=1, linked=0`; Core-Mappings weiterhin **1** (kein Duplikat); **Core-SHA256
  vor/nach Lauf 2 IDENTISCH**. Exit-Kriterium „Apply → Apply → identischer State, keine Duplikate" erfüllt. Core danach
  aus Backup restauriert (144 Items, 0 Mappings), Test-Ordner entfernt.

**Wirkt auch für den HITL-Pfad (S1):** Apply-Executor ruft dieselbe `ExecuteAsync` → Resume-twice erzeugt kein Duplikat.

**Residual (bewusst offen):** Der Guard stützt sich auf die Core-Mapping-Relation, die am Ende eines Laufs als **Batch**
geschrieben wird. Stirbt der Prozess MITTEN im Lauf (nach `CreateIssue`, vor dem Core-Write), hat der Core kein Mapping
und ein Re-Run könnte den CREATE doch duplizieren. Robuste Absicherung = **inkrementelle (per-Op) Mapping-Persistenz**
statt Batch — zurückgestellt, da (a) der Hauptrisikofall Resume-twice/Re-Run abgedeckt ist und (b) es einen echten
`--execute`-Lauf zum Testen braucht.

## S4 — Muster ausrollen: `pbi-update`, `decision`, `ingestion`

**Ziel.** Dieselbe `RequestPort`+Checkpoint-Form auf die übrigen agentischen Stufen übertragen; je Stufe entfallen die
`-review`/`-apply`-Runner.

**Warum.** Erst nach einer stabilen Referenz (S1–S3) ist der Roll-out risikoarm und konsistent. Nebeneffekt: die
Runner-Duplikation des lebenden Strangs (Decision §5) sinkt **strukturell**, nicht durch kosmetisches Refactoring.

**Vorgehen.** Pro Stufe: Gate-Verdict → RequestPort → Apply-Executor; Prozess-State minimal; gemeinsame Plumbing
(ChatClient/Pipeline/Tools/RunContext) in eine dünne Host-Composition ziehen, während man die Stufe ohnehin anfasst.

**Erwartete Beobachtung.** Jede Stufe = ein MAF-Lauf mit Human-Gate; CLI reduziert auf `start`/`respond`.

**Exit-Kriterium.** Für jede migrierte Stufe: alter `-review`/`-apply`-Runner entfernt (oder als Legacy markiert),
Ergebnis-Parität zum alten Pfad belegt.

**Evidenzpfad.** je Stufe ein Referenzlauf-runId + Paritäts-Notiz.

**Risiken.** `ingestion` hat den größten Blast-Radius (erste Core-Mutation) → als **letzte** der drei migrieren.

**Abhängigkeit.** S1–S3 grün.

**Beleg (deterministisch, KEIN LLM):** leeres Ingestion-Delta (`s4-verify-empty`) → Derive 0 Ops, 0 unplaced → Maker

## S5 — Forschungs-Spikes archivieren (kein Merge)

**Ziel.** Den lebenden Strang optisch/strukturell vom eingefrorenen Forschungs-Backlog trennen.

**Warum.** ~2/3 der Runner sind frozen Spikes (Ledger-/Evaluator-Kapitel, `claim-*`, `topic-*`, `contract-*`, …;
memory: *Historie*). Sie sind **bewusst separat** für Attribuierbarkeit (exploratives Projekt) — Mergen würde
Experiment-Evidenz vermischen und wäre wissenschaftlich falsch. Archivieren macht den roten Faden im Code sichtbar,
**ohne** Evidenz zu zerstören.

**GARANTIE (unmissverständlich).** „Archivieren" = **einsortieren, nicht entfernen**. Alle Spike-Kommandos bleiben
**aufrufbar** (Command-Dispatch in `Program.cs` bleibt bestehen), der Code bleibt compilierbar, es gibt **keine
Logikänderung**. Vorgehen ist **append-/reorganize-only**: kein Löschen von Kommandos, Runnern oder Run-Outputs. Ein
tatsächliches Entfernen aus der CLI wäre eine **separate, explizite** Entscheidung — passiert hier nicht nebenbei.
Ebenso: Run-Outputs unter `runs/` sind append-only (kein Purge-Code) und bleiben vollständig erhalten.

**Vorgehen.** Spikes in einen `archive/`-Namespace/Ordner verschieben **oder** in `Program.cs` klar gruppieren
(„frozen research"-Block mit Kommentar). Keine Logikänderung.

**Erwartete Beobachtung.** `Program.cs`-Dispatch zeigt lebenden Strang (~20–25 Kommandos) getrennt vom Archiv.

**Exit-Kriterium.** Ein Kollege erkennt aus der Dispatch-Struktur, was live ist. Build unverändert grün.

**Evidenzpfad.** Diff `Program.cs` + Ordnerstruktur.

**Risiken.** Referenzen/Namespaces beim Verschieben — nur nach grünem Build abschließen.

**Abhängigkeit.** unabhängig von S1–S4 (jederzeit machbar); sinnvoll nach S4, damit migrierte Stufen sauber einsortiert
sind.

### S5 — ERGEBNIS (2026-07-21): ☑ verifiziert

Gewählte Umsetzung: **klare Gruppierung in `Program.cs` (Banner + Hilfetext), KEIN physisches Verschieben/Namespace-
Umbau** — Letzteres wäre riskant (Referenz-Bruch) und widerspräche „keine Logikänderung". Umgesetzt:

**Hinweis:** Die Kategorisierung ist eine abgeleitete Landkarte (kein Code-Verhalten). Grenzfälle
(`operationalization-audit`, einzelne `l4-*`) im Zweifel gegen den aktuellen Arbeitsstand verifizieren — Korrektur ist

## S6 — Ausblick A: Stufen zu einem Super-Workflow komponieren

**Ziel.** Die migrierten Stufen-Workflows zu einem durchgehenden MAF-Graphen verbinden (Stufe→Stufe als Edges, je
Human-Gate ein RequestPort, ein Checkpoint-Store).

**Warum.** Wenn die drei Invarianten aus Decision §4 (Store-Abstraktion, Core-vs-Prozess-State-Trennung, typisierte

resumebar.

**Risiken.** Superstep-Checkpoint-Größe über mehrere Stufen — Prozess-State weiterhin minimal, Core extern.

**Abhängigkeit.** S1–S4 stabil.

- `pipeline/PipelineComposedWorkflow.cs` — komponiert **ingest → pbi-update** zu EINEM MAF-Graphen mit ZWEI RequestPorts:

## S7 — Durabler DB-`ICheckpointStore`

**Ziel.** Checkpoints (und später der Core) in die Ziel-DB statt auf Platte.

**Warum.** Der Autor plant ohnehin eine DB-Persistenz. `ICheckpointStore<JsonElement>` ist ein 3-Methoden-Interface
(`CreateCheckpointAsync`/`RetrieveCheckpointAsync`/`RetrieveIndexAsync`) — ein kleiner, MAF-nativer Seam. Dieselbe DB
kann Core und Checkpoints tragen; der Store-Wechsel ist ein Einzeiler am `CheckpointManager.CreateJson(...)`.

**Exit-Kriterium.** `FileSystemJsonCheckpointStore` gegen DB-Store getauscht, S1-Lauf unverändert grün.

**Risiken.** Trust-Boundary/Zugriffsrechte des Stores (Docs) — Secrets nie in den Prozess-State.

**Abhängigkeit.** frühestens nach S1; sinnvoll parallel zur allgemeinen Core→DB-Migration.

### S7 — STATUS (2026-07-21): ⊘ BEWUSST ZURÜCKGESTELLT (an Core→DB gekoppelt)

Keine offene Lücke. Begründung: Die Tausch-Naht ist bereits **by construction** bewiesen — der eingebaute
`FileSystemJsonCheckpointStore` **ist** ein `ICheckpointStore<JsonElement>` (durabel auf Platte, prozessübergreifend
resumebar, in S0–S6 belegt). Ein DB-Backend ist derselbe **Einzeiler-Tausch** am `CheckpointManager.CreateJson(...)`.
Solange der **Core** JSON-basiert ist, wäre eine separate Checkpoint-DB verfrühte Infrastruktur. S7 wird daher erst
**gemeinsam mit der Core→DB-Migration** umgesetzt (dann tragen Core + Checkpoints dieselbe DB, 3-Methoden-Interface).
Fortfahren ohne S7 hat **keine funktionale Konsequenz**.
