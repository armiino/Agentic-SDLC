# Gesamtplan für die Weiterentwicklung des evidenzbasierten, agentischen SDLC-Systems

## 1. Vision des Systems

Ziel des Systems ist es, Informationen aus Stakeholder-, Kunden- und Sprint-Meetings schrittweise in belastbare, nachvollziehbare und operativ nutzbare Softwareentwicklungsartefakte zu überführen. Dabei soll das System nicht einfach aus einem Transkript direkt Requirements oder GitHub Issues generieren. Stattdessen wird eine kontrollierte Evidenzkette aufgebaut, in der jede Information eine klar definierte Herkunft, einen Status und eine Version besitzt.

Die langfristige Vision ist ein System, das über mehrere Meetings und Sprints hinweg einen wachsenden Projektzustand verwaltet. Neue Aussagen sollen nicht isoliert verarbeitet werden, sondern mit bestehenden Requirements, Risiken, Architekturentscheidungen, offenen Fragen und GitHub Issues in Beziehung gesetzt werden. Das System soll erkennen können, ob eine neue Aussage ein neues Artefakt erzeugt, ein bestehendes Artefakt konkretisiert, einen früheren Punkt widerspricht, ein geschlossenes Thema erneut öffnet oder keine Änderung erfordert.

Das System soll dabei agentische Fähigkeiten gezielt dort einsetzen, wo semantische Interpretation, Exploration, Planung oder Revision erforderlich sind. Verbindliche Garantien wie ID-Stabilität, Versionierung, Persistenz, Provenienz und Statusregeln bleiben deterministisch kontrolliert.

Die zentrale Architekturidee lautet daher:

```text
Transkript und Meetings
        ↓
Evidence Ledger
        ↓
verifizierte Baseline-Artefakte
        ↓
verankerte agentische Ableitungen
        ↓
offene, menschlich zu bestätigende Vorschläge
        ↓
persistenter Projektzustand
        ↓
operative GitHub-Arbeitseinheiten
```

Der Agent arbeitet nicht in einer uneingeschränkten offenen Welt. Er erhält eine kontrollierte Projektumgebung, domänenspezifische Werkzeuge und externe Feedbacksignale. Innerhalb dieser Grenzen darf er selbstständig planen, suchen, auswählen, ableiten und korrigieren.

## 2. Bereits erreichter Stand

Das bestehende System besitzt bereits einen starken und differenzierten Kern. Aus einem Rohtranskript wird zunächst ein Evidence Ledger erzeugt. Aussagen werden extrahiert, kanonisiert, kategorisiert, mit stabilen Claim-IDs versehen und bei Bedarf menschlich adjudiziert. Der Ledger bildet damit die kontrollierte Wissensbasis.

Aus diesem Ledger entstehen Baseline-Artefakte wie Requirements, Architekturartefakte, Risiken und offene Fragen. Diese Artefakte besitzen Referenzen auf die zugrunde liegenden Claim-IDs. Damit bleibt jeder Baseline-Punkt bis zur ursprünglichen Evidenz zurückverfolgbar.

Darauf aufbauend existiert ein generischer Derivation-Motor. Dieser kann abhängig von Konfiguration und Prompt unterschiedliche Zielartefakte erzeugen, beispielsweise Risiken aus Requirements und Architektur oder abgeleitete Requirements aus bestehenden Requirements. Der stärkste aktuelle Agentenpfad ist der Reflect-Arm. Dieser kombiniert Umweltentdeckung, Tool-Nutzung, Rechenschaft, externe Prüfung, begrenzte Revision und gezielte Wiederverwendung des vorherigen Entwurfs. Der Reflect-Loop ist zusätzlich als MAF-nativer Graphzyklus mit konditionalen Kanten realisiert.

Damit ist die grundlegende agentische Architektur bereits vorhanden:

```text
Agentischer Producer
        ↓
externe deterministische und semantische Prüfung
        ↓
Pass → Abnahme
Fail → Entwurf + Feedback zurück
        ↓
gezielte Revision
        ↓
erneute Abnahme
```

Der nächste Entwicklungsschritt ist deshalb nicht, einen noch „echteren“ Agenten zu bauen. Der nächste Schritt besteht darin, die bisher lokal erzeugten Artefakte in einen dauerhaften, sprintübergreifenden Projektprozess und anschließend in eine kontrollierte GitHub-Operationalisierung zu überführen.

## 3. Zentrale fachliche Ebenen

Das System sollte künftig drei Wissensebenen klar voneinander trennen.

### 3.1 Ebene 1: Extrahierte Projektwahrheit

Diese Ebene enthält ausschließlich Informationen, die direkt aus Meetings und Transkripten stammen und durch den Evidence-Prozess abgesichert wurden.

Beispiele:

```text
CLAIM-37:
Ein Login Screen soll bereitgestellt werden.

REQ-12:
Das System muss einen Login Screen bereitstellen.

sourceClaimIds:
- CLAIM-37
```

Typische Herkunft:

```text
origin = Extracted
```

Diese Ebene ist Closed World. Sie beschreibt, was tatsächlich gesagt, bestätigt oder explizit vereinbart wurde.

### 3.2 Ebene 2: Verankerte Ableitungen

Hier erzeugt der Reflect-Agent neue Artefakte, die nicht wörtlich im Meeting genannt wurden, aber nachvollziehbar aus bestehenden Projektartefakten abgeleitet werden können.

Beispiel:

```text
DREQ-04:
Der Login Screen muss Eingabefelder für E-Mail-Adresse und Passwort bereitstellen.

sourceArtifactItemIds:
- REQ-12
```

Typische Herkunft:

```text
origin = Derived
```

Diese Ebene erweitert den Projektumfang, bleibt jedoch auf bestehende Requirements, Architekturpunkte oder andere freigegebene Artefakte verankert.

### 3.3 Ebene 3: Open-World-Vorschläge

Ein späterer Agent kann weitergehende Vorschläge erzeugen, die nicht zwingend aus einem bestehenden Artefakt folgen.

Beispiel:

```text
OREQ-03:
Das System sollte Multi-Faktor-Authentifizierung unterstützen.
```

Mögliche Herkunft:

```text
origin = OpenWorldProposal
status = Proposed
reviewRequired = true
```

Solche Vorschläge dürfen ebenfalls IDs besitzen. Ihre ID bedeutet jedoch lediglich, dass sie stabil adressierbar und versionierbar sind. Sie bedeutet nicht, dass sie bereits Projektwahrheit darstellen.

Nach menschlicher Bestätigung kann ein Vorschlag in ein akzeptiertes Requirement überführt werden:

```text
OREQ-03
        ↓ Human Approval
REQ-27
sourceProposalId = OREQ-03
```

Diese Trennung ist essenziell, damit extrahierte Fakten, begründete Ableitungen und offene Empfehlungen nicht vermischt werden.

## 4. Warum die GitHub-Kette zunächst ohne Datenbank gebaut werden sollte

Eine Datenbank ist langfristig sinnvoll. Sie löst aber nicht die zentrale fachliche Frage:

> Wie werden fachliche Artefakte sinnvoll in operative GitHub-Arbeitseinheiten überführt?

Bevor eine Datenbank eingeführt wird, sollte zunächst der vollständige GitHub-Planungsprozess mit den bestehenden JSON-Artefakten aufgebaut werden. Dadurch kann die fachliche Logik isoliert getestet werden.

Die erste Zielkette lautet:

```text
lokale Artefakte
        ↓
Issue Planning Agent
        ↓
IssuePlan.json
        ↓
externe Validierung und Reflect-Loop
        ↓
freigegebener Issue Plan
        ↓
GitHub Connector
        ↓
GitHub Issue
        ↓
lokales Mapping
```

Die Vorteile dieses Vorgehens sind:

1. Die bestehende Evidenzkette bleibt unangetastet.
2. Fehler lassen sich eindeutig der Issue-Planungslogik zuordnen.
3. Es entsteht zunächst keine zusätzliche Komplexität durch Migration, Retrieval und Synchronisation.
4. Der bereits entwickelte Reflect-Motor kann in einer neuen Domäne wiederverwendet werden.
5. Der Datenvertrag zwischen Projektartefakten und GitHub wird früh stabilisiert.
6. Die spätere Datenbank erhält ein empirisch erprobtes fachliches Modell statt eines spekulativ entworfenen Schemas.

Die Persistenz sollte jedoch von Anfang an hinter einer abstrakten Repository-Schicht verborgen werden. Dadurch kann zunächst JSON verwendet und später SQLite eingesetzt werden, ohne Agentenprompts, Tools oder Workflowlogik neu zu schreiben.

```text
Agent
→ AI Functions
→ ProjectStateRepository
→ heute JSON
→ später SQLite
```

## 5. Phase A: Fachlichen GitHub-Planungsprozess definieren

### Status 2026-07-16

Der erste plan-only Durchstich ist umgesetzt, aber noch ohne echten GitHub-Zugriff.

Bereits erledigt:

```text
AcceptedIssuePlanView
  -> GithubReconciliationInput
  -> GithubActionPlan
  -> GithubActionPlanGate
```

Zusaetzlich ist der agentische plan-only Knoten vorbereitet:

```text
GithubReconciliationInput
  -> GithubReconciliationAgent[Tools]
  -> GithubActionPlanGate[det]
  -> GithubReconciliationFinalize
```

Neue CLI:

```bash
github-reconciliation seed <accepted-issue-plan-dir|runId>
github-reconciliation check <accepted-issue-plan-dir|runId> <github-action-plan.json>
```

Validierter Lauf:

```text
input: runs/l4-issuplanning/20260716_132545_823a03/plan/applied/accepted-issue-plan.json
actions=19
gate=pass
errors=0
warnings=0
CREATE=9
NEEDS_REVIEW=4
NO_CHANGE=6
existingIssues=0
existingMappings=0
```

Dry-run validiert:

```text
github-reconciliation agent 20260716_132545_823a03 --dry-run --repo local/pflege-app
Graph Build()-bar
```

Echter Agentenlauf:

```text
runId=20260716_144616_19be8e
gate=pass
actions=19
toolCheckRounds=1
CREATE=9
NEEDS_REVIEW=4
NO_CHANGE=6
existingIssues=0
existingMappings=0
```

Einordnung:

- Der Knoten schreibt nicht nach GitHub.
- `existingIssues` und `existingMappings` sind aktuell leer bzw. optional lokal per JSON ladbar.
- Der spaetere GitHub-MCP-Adapter soll diesen Reconciliation-Input fuellen, nicht den Requirements-/IssuePlanning-Prozess
  umgehen.
- GitHub read-only und GitHub write sind weiterhin offen.
- Naechster Schritt ist HumanReview/Apply fuer `GithubActionPlan` und danach ein read-only GitHub/MCP-Adapter fuer
  `existingIssues`/`existingMappings`.

### 5.1 Rolle von GitHub

GitHub sollte nicht die vollständige Wissensbasis des Systems sein. Es ist die operative Umsetzungsebene.

Die Aufgabenteilung lautet:

```text
Projektzustand:
Requirements, Risiken, Architektur, Herkunft, Versionen

GitHub:
Issues, Assignees, Milestones, Labels, Kommentare, Umsetzung
```

Nicht jedes Requirement wird automatisch zu einem Issue. Ein Requirement kann:

* ein eigenes Issue erzeugen,
* mit anderen Requirements gebündelt werden,
* mehrere Issues erzeugen,
* Acceptance Criterion eines bestehenden Issues sein,
* zunächst noch nicht umsetzungsreif sein,
* nur als offene Frage oder Architekturentscheidung bestehen bleiben.

Der GitHub-Agent darf deshalb nicht einfach jedes Requirement eins zu eins exportieren.

### 5.2 Rolle des GitHub-Agenten

Der Agent sollte als **Issue Planning and Reconciliation Agent** konzipiert werden.

Sein Ziel lautet:

> Überführe freigegebene, noch nicht ausreichend operativ abgebildete Projektartefakte in nachvollziehbare GitHub-Arbeitseinheiten oder aktualisiere bestehende Arbeitseinheiten.

Er entscheidet semantisch zwischen:

```text
CREATE
UPDATE
LINK
REOPEN
NO_CHANGE
NEEDS_REVIEW
```

Er schreibt zunächst keine Issues direkt. Er erzeugt einen Issue Plan.

### 5.3 Issue-Plan-Datenvertrag

Der wichtigste neue Datenvertrag ist ein expliziter Issue Plan.

Beispiel:

```json
{
  "planId": "IPLAN-014",
  "operation": "CREATE",
  "title": "Implement login screen",
  "sourceItemIds": [
    "REQ-12",
    "DREQ-04",
    "DREQ-05",
    "ARCH-03"
  ],
  "acceptanceCriteria": [
    "An E-Mail input field is displayed.",
    "A password field masks user input.",
    "Invalid input is rejected.",
    "Authentication uses the configured identity provider."
  ],
  "labels": [
    "frontend",
    "authentication"
  ],
  "dependencies": [],
  "reason": "The requirements jointly describe one implementable login feature.",
  "requiresHumanReview": true
}
```

Der Issue Plan ist die kontrollierte Grenze zwischen fachlichem Projektzustand und GitHub.

### 5.4 Deterministische Prüfungen des Issue Plans

Der Host beziehungsweise ein Executor prüft verbindlich:

```text
- Existieren alle sourceItemIds?
- Sind alle Quellartefakte freigegeben?
- Sind die Quellartefakte für die Operationalisierung zugelassen?
- Gibt es bereits ein GitHub-Mapping?
- Ist CREATE erlaubt oder wäre UPDATE/NO_CHANGE korrekt?
- Ist der Titel vorhanden?
- Sind Acceptance Criteria vorhanden?
- Enthält der Plan unzulässige IDs?
- Ist der Plan intern eindeutig?
- Wurde genau eine Operation angegeben?
```

Diese Prüfungen bleiben deterministisch.

### 5.5 Semantische Prüfung

Ein externer Judge oder ein separater Gate-Schritt bewertet:

```text
- Ist das Issue sinnvoll geschnitten?
- Ist es tatsächlich umsetzbar?
- Wurden unabhängige Aufgaben fälschlich gebündelt?
- Sind die Acceptance Criteria durch die Quellen gedeckt?
- Sind Architektur- oder Risikobezüge korrekt dargestellt?
- Wird ein bestehendes Issue unnötig dupliziert?
```

Auch hier kann der Reflect-Motor wiederverwendet werden:

```text
Issue Planning Agent
→ Gate
→ Pass
oder
→ Issue Plan + Feedback zurück
→ gezielte Revision
```

### 5.6 Plan-only-Modus

Der erste produktive Schritt sollte ausschließlich ein Plan-only-Modus sein.

Ausgabe:

```text
issue-plans/
  IPLAN-001.json
  IPLAN-002.json
  issue-plan-report.json
```

Noch keine Veränderung auf GitHub.

Dadurch kann bewertet werden:

* Ist die Issue-Granularität sinnvoll?
* Werden Artefakte korrekt gruppiert?
* Werden Duplikate erkannt?
* Sind Acceptance Criteria brauchbar?
* Ist die Provenienz nachvollziehbar?

Erst wenn diese Stufe stabil ist, sollte GitHub schreibend angebunden werden.

## 6. Phase B: JSON-basierte Repository-Schicht einführen

Bevor GitHub integriert wird, sollte eine kleine Repository-Abstraktion eingeführt werden.

Sie kapselt:

```text
- Artefakte laden
- Items nach ID finden
- Relationen auflösen
- bestehende Mappings lesen
- Issue Plans speichern
- GitHub-Mappings speichern
- Snapshots exportieren
```

Wichtig ist, dass die Tools des Agenten nicht direkt auf Dateipfade zugreifen.

Schlecht:

```text
read_file("runs/.../requirements.json")
```

Besser:

```text
get_project_item("REQ-12")
get_unmapped_items(...)
get_related_items("REQ-12")
```

Die erste Implementierung darf intern weiterhin deine vorhandenen JSON-Dateien lesen.

Mögliche Verzeichnisstruktur:

```text
project-state/
  artifacts/
    requirements.json
    architecture.json
    risks.json
    open-questions.json
  derived/
    derived-requirements.json
    derived-risks.json
  proposals/
    open-world-requirements.json
  issue-plans/
  github-mappings.json
  snapshots/
```

Diese Struktur ist nur eine Übergangslösung. Entscheidend ist die stabile Repository-Schnittstelle.

## 7. Phase C: Tools für den Issue Planning Agent

Der Agent sollte schmale domänenspezifische Tools erhalten.

### 7.1 Projektartefakte finden

```text
list_operationalizable_items(
    types?,
    statuses?,
    origins?
)
```

Damit entdeckt der Agent freigegebene Items, die grundsätzlich operativ abbildbar sind.

### 7.2 Einzelne Artefakte lesen

```text
get_project_item(itemId)
```

Rückgabe:

```text
Text
Status
Origin
Version
Quell-IDs
Relationen
bestehendes GitHub-Mapping
```

### 7.3 Verwandte Artefakte finden

```text
get_related_project_items(itemId)
```

Beispiele:

```text
Requirement → Architecture
Requirement → Risk
Requirement → Open Question
Requirement → Derived Requirement
```

### 7.4 Noch nicht operationalisierte Artefakte finden

```text
get_unmapped_items(
    types,
    statuses,
    origins
)
```

### 7.5 Bestehende GitHub-Abbildung prüfen

```text
get_github_mapping(itemId)
```

### 7.6 Bestehende Issues suchen

Zunächst kann diese Funktion gegen lokale Mapping-Dateien oder einen Read-only-GitHub-Zugriff arbeiten:

```text
search_github_issues(query, labels?, state?)
```

### 7.7 Issue Plan speichern

```text
save_issue_plan(plan)
```

Der Agent schreibt damit keinen GitHub-Zustand, sondern nur einen Vorschlag.

### 7.8 Optional: Kein Issue erforderlich

```text
mark_not_operationalized(
    itemIds,
    reason
)
```

Damit muss der Agent nicht künstlich jedes Artefakt in ein Issue verwandeln.

## 8. Phase D: GitHub zunächst read-only anbinden

Vor schreibenden Operationen sollte der GitHub MCP Server zunächst nur lesend verwendet werden.

Ziele:

```text
- bestehende Issues suchen
- Issue-Titel und Beschreibung lesen
- Status und Labels lesen
- Duplikate erkennen
- vorhandene Beziehungen prüfen
```

Der Agent kann dann bereits entscheiden:

```text
CREATE
UPDATE
LINK
NO_CHANGE
REOPEN
```

Er darf die Entscheidung aber nur als Plan speichern.

### Beispiel

Ein bestehendes Requirement:

```text
REQ-12:
Das System muss einen Login Screen bereitstellen.
```

Abgeleitete Requirements:

```text
DREQ-04:
E-Mail-Feld

DREQ-05:
Passwortfeld
```

Der Agent findet GitHub Issue `#84`:

```text
Create basic authentication screen
```

Dann erzeugt er keinen CREATE-Plan, sondern:

```json
{
  "operation": "UPDATE",
  "targetIssue": 84,
  "sourceItemIds": ["REQ-12", "DREQ-04", "DREQ-05"],
  "proposedChanges": {
    "acceptanceCriteria": [
      "Display an E-Mail input field.",
      "Display a masked password field."
    ]
  }
}
```

## 9. Phase E: Human Review für Issue Plans

Vor der ersten schreibenden GitHub-Integration sollte jeder Issue Plan menschlich geprüft werden.

Mögliche Entscheidungen:

```text
approve
reject
needs_revision
merge_with_other_plan
split_plan
```

Diese Entscheidungen sollten ebenfalls als Artefakte gespeichert werden.

Beispiel:

```json
{
  "planId": "IPLAN-014",
  "decision": "approve",
  "reviewer": "human",
  "reason": "The scope and acceptance criteria are appropriate."
}
```

Diese Review-Entscheidungen werden später Bestandteil des Project State und können bei zukünftigen Sprints helfen.

## 10. Phase F: Deterministischen GitHub Connector bauen

Erst nach Plan-only und Human Review erfolgt die schreibende Integration.

Wichtig:

> Der Agent plant. Der Connector führt aus.

Der Connector erhält einen freigegebenen Issue Plan und führt deterministisch GitHub-Operationen aus.
Die erste Implementierung nutzt einen dünnen Host-HTTP-Adapter gegen die GitHub REST API. Der geplante GitHub-MCP-Adapter
kann später dieselbe Boundary ersetzen.

Mögliche Operationen:

```text
CREATE
UPDATE
REOPEN
LINK
COMMENT
```

Der Connector prüft vorher erneut:

```text
- Plan freigegeben?
- Operation erlaubt?
- Ziel-Issue noch vorhanden?
- Issue inzwischen verändert?
- Mapping bereits vorhanden?
- Idempotenz-Key bereits verwendet?
```

Nach erfolgreicher Ausführung speichert der Connector das Mapping:

```json
{
  "projectItemIds": [
    "REQ-12",
    "DREQ-04",
    "DREQ-05"
  ],
  "repository": "org/project",
  "issueNumber": 84,
  "issueUrl": "...",
  "operation": "CREATE",
  "createdFromPlanId": "IPLAN-014",
  "syncedAt": "..."
}
```

Die Mapping-Persistenz muss deterministisch sein.

Aktueller Stand 2026-07-17:

```text
github-write dry-run:
  implementiert
  erzeugt github-write-dry-run.json
  blockiert NEEDS_REVIEW und ungueltige targetIssueNumber

github-write execute:
  implementiert
  braucht --confirm-write
  liest Token nur aus Umgebungsvariable, Default GITHUB_TEST_TOKEN
  persistiert Token nicht
  erzeugt github-write-execution.json
  erzeugt github-mappings-created.json
  blockiert Wiederholung ohne --allow-repeat, wenn Execution-Artefakt existiert
```

Unterstuetzte Operationen:

```text
CREATE  -> GitHub Issue erstellen
UPDATE  -> bestehendes Issue aktualisieren
REOPEN  -> bestehendes Issue wieder oeffnen
LINK    -> kein GitHub Write, Mapping persistieren
NO_CHANGE -> skipped
```

Noch offen:

- vorhandene GitHub-Mappings vor Write als Idempotenz-/Duplikatpruefung laden
- echte Mapping-Persistenz im ProjectStateRepository statt nur JSON-Output
- GitHub-MCP-Adapter als Alternative zum Host-HTTP-Adapter
- optionaler COMMENT-Support
- Reconciliation nach Write: Issue-Status und Mapping deterministisch zuruecksynchronisieren

## 12. Phase G: Erst jetzt SQLite einführen

Sobald die GitHub-Kette fachlich funktioniert, sollte die JSON-Implementierung durch SQLite ersetzt werden.

Das ist der richtige Zeitpunkt, weil nun bekannt ist:

```text
- welche Entitäten tatsächlich gebraucht werden,
- welche Relationen relevant sind,
- welche Abfragen der Agent stellt,
- welche Statusübergänge vorkommen,
- welche GitHub-Mappings erforderlich sind,
- welche Versionierung gebraucht wird.
```

Die Repository-Schnittstelle bleibt gleich.

```text
JsonProjectStateRepository
        ↓ austauschen
SqliteProjectStateRepository
```

### 12.1 Minimaler Datenbankumfang

```text
meetings
transcripts
claims
project_items
item_versions
item_relations
item_evidence
review_decisions
issue_plans
github_mappings
sprints
runs
```

### 12.2 Project Items vereinheitlichen

Statt für jeden Artefakttyp sofort eigene Tabellen zu bauen, kann zunächst eine generische `project_items`-Tabelle verwendet werden:

```text
item_id
item_type
origin
current_status
current_version
first_seen_sprint
last_seen_sprint
```

Die Texte und Versionen liegen in:

```text
item_versions
```

Relationen liegen in:

```text
item_relations
```

Evidenz liegt in:

```text
item_evidence
```

Damit kann ein Requirement mit Claims, Risiken, Architekturpunkten und GitHub Issues verknüpft werden.

## 13. Phase H: Living Requirements Document

Sobald ein persistenter Project State existiert, sollte ein lebendes Requirements-Dokument nicht mehr manuell gepflegt werden.

Es wird deterministisch aus dem aktuellen Projektzustand erzeugt.

Beispiel:

```markdown
# Requirements

## REQ-12 – Login Screen

Status: Accepted  
Origin: Extracted  
Version: 3  
Sources: CLAIM-37

Das System muss einen Login Screen bereitstellen.

### Verankerte Ableitungen

- DREQ-04 – Eingabefeld für E-Mail-Adresse
- DREQ-05 – Maskiertes Passwortfeld

### Verknüpfte Architektur

- ARCH-03 – Externer Identity Provider

### Verknüpfte Risiken

- DRISK-07 – Fehlkonfiguration der Authentifizierung

### GitHub

- Issue #84 – Implement login screen
```

Das Dokument ist eine Sicht auf die DB, nicht die einzige Wahrheit.

## 14. Phase I: Zweites Meeting und Sprint-Workflow

Erst jetzt sollte der eigentliche inkrementelle Sprint-Workflow gebaut werden.

### 14.1 Eingang

```text
neues Sprint-Transkript
```

### 14.2 Neuer Delta Ledger

Das neue Meeting wird erneut durch den Ledger-Prozess verarbeitet.

Wichtig:

```text
neue Claim-IDs
meetingId
sprintId
Transcript-Segment-Referenzen
```

### 14.3 Impact Agent

Der Agent erhält nicht die gesamte Datenbank. Er bekommt die neuen Claims und kontrollierte Suchtools.

Ziel:

> Identifiziere bestehende Projektartefakte, die durch die neuen Aussagen betroffen sind, und schlage nachvollziehbare Änderungsoperationen vor.

Der Impact Agent ist die fachliche Stelle, an der neue Sprint-Aussagen gegen den bestehenden Project State gematcht
werden. Diese Aufgabe darf nicht erst dem GitHub-Agenten überlassen werden. Der GitHub-Agent kennt den operativen
GitHub-Zustand, aber er soll nicht allein entscheiden, ob eine neue Aussage fachlich ein neues Requirement, eine
Konkretisierung, eine Änderung oder nur eine Wiederholung eines bereits erledigten Themas ist.

Mögliche Operationen:

```text
CREATE
UPDATE
REOPEN
SUPERSEDE
LINK
NO_CHANGE
NEEDS_REVIEW
```

Erweiterte Impact-Klassifikation:

```text
NO_CHANGE
CLARIFICATION
CHANGE_REQUEST
REOPEN_NEEDED
OBSOLETE
NEW_REQUIREMENT
NEEDS_REVIEW
```

Beispielfall:

```text
Sprint-Transkript spricht Thema X an.
Thema X gehoert zu einem Bereich, der fachlich bereits umgesetzt ist.
Es gibt kein offenes GitHub-Issue mehr.
```

Erwartetes Verhalten:

```text
Impact Agent:
  Thema X auf bestehendes CAN-REQ-* / ProjectItem mappen.
  Klassifizieren: NO_CHANGE oder CLARIFICATION, falls keine neue fachliche Änderung entsteht.

L4 Refresh:
  Kein neuer kanonischer Stand, falls NO_CHANGE.
  Neue Requirement-Version nur, falls CLARIFICATION/CHANGE_REQUEST fachlich relevant ist.

Readiness:
  Nur betroffene neue/geaenderte Requirement-Versionen bewerten.

Issue Planning:
  Kein neues Issue, falls NO_CHANGE.
  UPDATE/CREATE/NEEDS_REVIEW nur, falls Readiness einen operativen Bedarf freigibt.

GitHub Reconciliation:
  Bestehende Mappings und geschlossene Issues pruefen.
  Bei geschlossenem Issue nicht automatisch wieder oeffnen.
  REOPEN oder Follow-up nur planen, wenn ProjectState/Impact/Readiness einen echten Bedarf zeigen.
```

Damit bleibt die Verantwortung getrennt:

```text
Impact Agent:
  Ist die neue Sprint-Aussage fachlich neu, aendernd oder nur wiederholend?

L4 / ProjectState:
  Welche kanonische Requirement-Version ist dadurch gueltig?

Readiness:
  Darf die Version operativ geplant werden?

L4IssuePlanningAgent:
  Wie soll die freigegebene Arbeit geschnitten werden?

GitHub Reconciliation:
  Welche GitHub-Aktion passt zu Plan, Mapping und realem Issue-Zustand?
```

```text
search_project_items(query, types, statuses)
get_item_history(itemId)
get_related_project_context(itemId)
get_linked_github_issue(itemId)
```


Der Agent kann daraus ableiten:

```text

```

## 16. Phase K: Memory erst nach funktionierendem Project State

Ein Langzeit-Memory-System sollte nicht vor der Project-State-Datenbank eingeführt werden.

Zuerst muss die autoritative Wahrheit stabil sein.

```text
Project State
= Beweis und Wahrheit

Memory
= selektiver Hinweis und Beschleuniger
```

Memory kann später enthalten:

```text
- wiederkehrende Review-Korrekturen,
- typische Fehlermuster,
- frühere Ablehnungsgründe,
- Stakeholder-Präferenzen,
- häufig relevante historische Entscheidungen.
```

Dieses Memory darf nie die einzige Quelle kritischer Informationen sein.

Ein sinnvoller späterer Vergleich wäre:

```text
A:
Host lädt relevante Historie deterministisch.

B:
Agent sucht relevante Historie selbst über Tools.

C:
Context Provider injiziert automatisch Memory.
```

Damit bleibt auch der Memory-Ausbau wissenschaftlich messbar.

## 20. Risiken und typische Fehler

### Zu frühe Datenbankarchitektur

Gefahr:

```text
Schema wird gebaut, bevor klar ist, welche Abfragen wirklich benötigt werden.
```

Gegenmaßnahme:

```text
Erst IssuePlan- und Sprint-Operationen mit JSON stabilisieren.
```

### GitHub wird zur Wahrheit

Gefahr:

```text

```

Gegenmaßnahme:

```text
Projektzustand bleibt fachlich autoritativ.
```

### Jedes Requirement wird ein Issue

Gefahr:

```text
Issue-Spam und schlechte Granularität.
```

Gegenmaßnahme:

```text
Issue Planning Agent + Gate + Human Review.
```

### Open-World-Vorschläge werden als Wahrheit behandelt

Gegenmaßnahme:

```text
eigene Origin- und Statusklasse.
```

### Agent schreibt direkt in die DB

Gefahr:

```text
verlorene Historie, inkonsistente IDs, fehlerhafte Statuswechsel.
```

Gegenmaßnahme:

```text
Agent schlägt Änderungen vor.
Deterministischer Commit führt sie aus.
```

### Agent greift direkt auf SQL zu

Gegenmaßnahme:

```text
schmale AI Functions über Repository.
```

### GitHub-Sync wird agentisch

Gegenmaßnahme:

```text

```

### Memory wird zur Wahrheit

Gegenmaßnahme:


### Schritt 9

CREATE-, UPDATE-, LINK-, REOPEN- und NO_CHANGE-Planung testen.

Stand 2026-07-16:

- `github-reconciliation agent` erzeugt plan-only einen `github-action-plan.json`.
- `GithubActionPlanGate` prueft Vollstaendigkeit, Operationen, Ziel-Issues und SourceRequirement-Bezug.
- `github-reconciliation-review` stellt den Plan in der generischen HumanReview-UI bereit.
- Default-Scope ist `needs-human`; `--scope all` zeigt die komplette Kontrollsicht.
- `github-reconciliation-apply` materialisiert nach HumanReview einen `accepted-github-action-plan.json`.
- Ohne `human-decisions.json` blockiert Apply erwartbar.

Damit ist Schritt 9 lokal und ohne GitHub-Write vorbereitet. Der spaetere Connector darf nur den akzeptierten Plan konsumieren.

Read-only GitHub-Umwelt:

- `github-snapshot issues` normalisiert vorhandene GitHub Issues in `github-issues-snapshot.json`.
- Provider:
  - Datei fuer reproduzierbare Tests
  - GitHub REST API als Default
  - optional `gh`
- Dieser Snapshot wird mit `github-reconciliation ... --issues <snapshot>` konsumiert.
- Reconciliation liest dadurch nicht selbst GitHub und bleibt als Agentenknoten austauschbar.

Beispiel:

```bash
dotnet run --project AgenticSdlc.Host/AgenticSdlc.Host.csproj -- github-snapshot issues owner/name --out runs/manual/github-snapshot-test
dotnet run --project AgenticSdlc.Host/AgenticSdlc.Host.csproj -- github-reconciliation agent 20260716_132545_823a03 --repo owner/name --issues runs/manual/github-snapshot-test/github-issues-snapshot.json
```

Alternative fuer spaeter:

- Ein zweiter read-only Vergleichsarm darf dem GitHub-Agenten direkte GitHub-MCP-Read-Tools geben.
- Dieser Arm bildet eher den "Agent erkundet live seine Umwelt"-Ansatz ab.
- Er soll gegen den Snapshot-/ProjectState-Pfad verglichen werden, nicht ungeprueft den Hauptpfad ersetzen.
- Bewertungskriterien:
  - Match-Qualitaet
  - Duplikatvermeidung
  - Stabilitaet ueber Wiederholungslaeufe
  - Auditierbarkeit
  - Reproduzierbarkeit
  - Toolcall-Kosten und Fehlgriffe
- Auch dieser MCP-Arm bleibt zunaechst plan-only; GitHub-Write bleibt separat nach HumanReview/Apply.

### Schritt 10

Einen deterministischen GitHub Connector für freigegebene Pläne bauen.

Input fuer diesen Schritt ist nicht der rohe Agentenplan, sondern:

```text
runs/github-reconciliation/<runId>/plan/applied/accepted-github-action-plan.json
```

Der Connector soll daraus kontrollierte GitHub-Operationen ableiten und erst nach expliziter Freigabe schreiben.

Stand 2026-07-16:

- `github-write dry-run` ist implementiert.
- Der Knoten konsumiert `accepted-github-action-plan.json`.
- Er schreibt nicht nach GitHub.
- Er berechnet deterministisch:
  - welche CREATE-Calls spaeter noetig waeren
  - welche UPDATE/REOPEN-Calls spaeter noetig waeren
  - welche LINK-Operationen nur lokale Mappings erfordern
  - welche NO_CHANGE-Actions keine Operation brauchen
  - welche NEEDS_REVIEW-Actions echten Write blockieren

Aktueller Testlauf:

```text
source=20260716_160450_cdeabe
actions=19
create=7
update=0
link=1
reopen=1
noChange=6
needsReview=4
blocked=4
readyForExecute=false
```

Bewertung:

- Der Write-Pfad ist vorbereitet, aber bewusst blockiert.
- Ein echter GitHub-Write darf erst gebaut/aktiviert werden, wenn HumanReview die NEEDS_REVIEW-Actions entschieden hat.
- Der Dry-Run ist der Vertrag fuer den spaeteren deterministischen Write-Executor.

Operationalization Audit:

- `operationalization-audit` ist als deterministisches Gate vor echtem Write ergaenzt.
- Der Knoten rekonstruiert die Kette:

```text
canonical-requirements-baseline
  -> requirements-readiness
  -> issue-planning-input
  -> accepted-issue-plan
  -> accepted-github-action-plan
  -> github-write-dry-run
```

Aktueller Lauf:

```text
canonical=69
readiness=69
issueInput=31
issuePlan=19
githubActions=19
coveredIssueInput=31/31
blockedRequirements=8
noChangeOnly=6
readyForGithubWrite=false
```

Zweck:

- Nachweisen, dass alles im IssuePlanningInput operativ behandelt wurde.
- Sichtbar machen, welche Requirements bewusst nicht in IssuePlanning gingen.
- Sichtbar machen, welche Requirements GitHub-Write blockieren.
- Echten Write verhindern, solange offene Review-/Readiness-Themen bestehen.

Open Requirements Review:

- Nicht im Delivery-IssuePlanning enthaltene Requirements werden nicht ignoriert.
- Sie laufen in einen separaten HumanReview-Pfad:

```text
Operationalization Audit
  -> open-requirements-review
  -> open-requirements-apply
  -> clarification-planning-input
  -> clarification-agent plan
```

Aktueller Lauf:

```text
open requirements=38
needs_decision=28 -> create_clarification_issue
needs_breakdown=8 -> break_down_required
deferred_or_optional=2 -> defer
clarificationItems=36
```

Ziel:

- Delivery-Issues bleiben nur fuer umsetzbare Anforderungen.
- Offene Entscheidungen und Breakdown-Bedarf werden als Klaerungs-/Discovery-Arbeit planbar.
- `clarification-agent plan` erzeugt daraus einen plan-only ClarificationPlan, der spaeter in Klaerungs-/Breakdown-Issues ueberfuehrt werden kann.
- Mensch oder Agent kann diese Klaerungs-Issues spaeter beantworten; die Antwort geht ueber Proposal/HumanReview/Apply zurueck in den ProjectState.

Aktueller Clarification-Agent Stand:

```text
mode plan:
  ClarificationPlanningInput
    -> ClarificationPlanningAgent[Tools]
    -> ClarificationPlanGate[det]
    -> Finalize

mode resolve:
  TBD-Contract fuer spaetere Loesungsvorschlaege
```

Validierter technischer Durchstich:

```text
clarification-plan seed: 36 items
gate: pass
dry-run: Graph buildbar, kein LLM
resolve --describe: Contract materialisiert
```

Erweiterter Durchstich 2026-07-17:

```text
clarification-agent plan agent:
  runId=20260717_084008_691527
  input=36 ClarificationPlanningInputItems
  output=18 ClarificationPlanItems
  gate=pass
  warnings=3

clarification-agent-apply:
  acceptedItems=18/18
  gate=pass

github-reconciliation seed ueber accepted-clarification-plan:
  actions=18
  gate=pass

github-write dry-run:
  create=16
  noChange=2
  blocked=0
  readyForExecute=True
```

Architekturentscheidung:

- ClarificationPlanning bleibt ein eigener fachlicher Knoten.
- GitHub-Reconciliation bleibt der gemeinsame plan-only GitHub-Knoten.
- Ein `accepted-clarification-plan.json` wird ueber `ClarificationPlanIssueProjection` in das bestehende IssuePlan-kompatible
  Format projiziert.
- Dadurch muss GitHub-Reconciliation nicht dupliziert werden.
- Spaeter kann dieselbe Projektion aus einer DB-View statt aus JSON-Dateien kommen.

Offen:

- Echten GitHub-Write weiterhin nur nach HumanReview/Apply aktivieren.
- GitHub-Mappings fuer Delivery- und Clarification-Issues persistieren.
- Clarification-Issues spaeter optional durch `clarification-agent resolve` oder einen Sprint-/GitHub-Kommentar-Agenten beantworten lassen.

## 23. Zentrale Architekturprinzipien

1. **Der Ledger schafft die kontrollierte Evidenzbasis.**
2. **Baseline-Artefakte repräsentieren explizit Gesagtes.**
3. **Der Reflect-Agent erzeugt verankerte neue Erkenntnisse.**
4. **Open-World-Vorschläge bleiben bis zur Bestätigung Vorschläge.**
5. **IDs bedeuten Adressierbarkeit, nicht automatisch Wahrheit.**
6. **Die Datenbank wird autoritativer Projektzustand, nicht das LLM-Memory.**
7. **Der Agent greift nur über kontrollierte Tools zu.**
8. **Agenten schlagen Änderungen vor; deterministischer Code committed sie.**
9. **GitHub bildet operative Arbeit ab, nicht die vollständige Projektwahrheit.**
10. **Technische Synchronisation bleibt deterministisch.**
11. **Semantische Interpretation darf agentisch sein.**
12. **Der Reflect-Arm ist der primäre produktive Agentenpfad.**
13. **Andere Arme bleiben Forschungs- und Kontrollbedingungen.**
14. **Memory wird erst ergänzt, wenn Project State und Historie stabil sind.**
15. **Jeder Ausbau muss ein konkretes Problem lösen und messbar bleiben.**
16. **GitHub-Writes muessen vor dem ersten Schreiben entwicklungsbrauchbar sein.**

Ein spaeterer Update-Prozess ist fuer Migration und laufende Aenderungen noetig, aber nicht die Standardloesung fuer initial duenne Issues.
Der produktive Pfad blockiert duenne `CREATE`-/`UPDATE`-Actions vor dem GitHub-Write ueber ein deterministisches Issue Quality Gate.
Dieses Gate verlangt nachvollziehbare Quellen, bekannte Kontexte, Umsetzungshinweise, Readiness und Acceptance Criteria.
Klaerungs-/`DISK`-Issues sind erlaubt, muessen aber als solche markiert sein und offene Entscheidungsfragen enthalten.

## Schlussfolgerung

Der sinnvollste nächste Schritt ist nicht der sofortige Aufbau einer vollständigen Datenbank. Zuerst sollte die fachliche GitHub-Operationalisierung mit den bestehenden lokalen Artefakten abgeschlossen werden. Dafür werden ein Issue-Plan-Datenvertrag, ein JSON-basiertes Repository, ein Issue Planning Reflect Agent, ein externes Gate, Human Review und ein deterministischer GitHub Connector benötigt.

Sobald dieser Prozess fachlich stabil ist, kann die Persistenz hinter derselben Repository-Schnittstelle von JSON auf SQLite umgestellt werden. Erst dann sollte das zweite Meeting beziehungsweise der inkrementelle Sprint-Workflow umgesetzt werden. Auf diese Weise entsteht die Datenbank nicht spekulativ, sondern auf Basis real benötigter Entitäten, Beziehungen, Abfragen und Statusübergänge.

Das langfristige Ergebnis ist ein agentisches, evidenzbasiertes SDLC-System, das nicht nur einzelne Artefakte erzeugt, sondern über mehrere Meetings hinweg einen nachvollziehbaren Projektzustand entwickelt, historische Informationen berücksichtigt, Änderungen kontrolliert ableitet und freigegebene Arbeitseinheiten bis nach GitHub operationalisiert.
